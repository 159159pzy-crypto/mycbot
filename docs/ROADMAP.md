# MyBot roadmap: foundation to finished bot

**Status: complete.** All eight milestones are delivered, verified, and
documented. This roadmap remains the standing overview of what "finished"
meant and how the work was sequenced; each milestone's dated
implementation plan lives under `docs/superpowers/plans/`, in the same
test-first task format as the Milestone 1 plans.

Decisions made for this roadmap, all of which held to the end:

- **Both platforms land together.** QQ (via an externally managed NapCat,
  OneBot v11 over WebSocket) and Telegram (official Bot API, long polling)
  were implemented in the same milestone so the platform-neutral
  `MessageEnvelope` contract was validated against two real platforms at
  once.
- **LLM access is OpenAI-compatible.** One `base_url` + `api_key` + `model`
  configuration reaches DeepSeek, Qwen, Kimi, OpenAI, or a local
  vLLM/Ollama endpoint. No provider-specific SDKs in the core.
- **Contracts stay authoritative.** `src/mybot/contracts` is the public
  surface (envelopes, decisions, reply plans, tools, memory, plugins).
  Milestones added behavior behind these contracts; the additions that
  proved necessary (e.g. `InboundEvent.sender_is_bot`) were backward
  compatible.

## Definition of done — final review

MyBot is "complete" when a self-hosted operator can run the Compose stack
plus an external NapCat and get, with tests and CI proving each property:

- [x] 1. The bot converses on **QQ and Telegram**: always in direct
  chats, and in groups when mentioned, replied to, or commanded, per
  `TurnDecision`. *(M2; adapters + turn policy + at-least-once streams.)*
- [x] 2. Replies come from an **LLM agent** (OpenAI-compatible endpoint)
  with persona, bounded conversation history, and graceful degradation
  when the LLM or a dependency is down. *(M3; turns audit table, token
  ceilings, explicit fallbacks.)*
- [x] 3. The agent uses **tools** — SearXNG web search and safe URL fetch
  — under the `ToolSpec`/`ToolResult` policy model, with citations
  surfaced through `ReplyPlan`. *(M4; SSRF guard, bounded tool loop,
  `Sources:` footer.)*
- [x] 4. The bot has **scoped long-term memory** (pgvector) honoring
  `MemoryScope`/`MemoryPrivacy`, with retrieval, conflict/supersede
  handling, revocation, and scheduled decay. *(M5; privacy enforced in
  SQL and code, `/forget`, maintenance lifecycle.)*
- [x] 5. **Plugins** ship real behavior: manifests validated against
  `PluginManifest`, executed in the isolated `plugin-runner`, exposing
  tools/hooks to the agent without new privileges. *(M6; broker with
  capability grants and refusal audit, example dice plugin.)*
- [x] 6. The **operator console** is authenticated and lets the operator
  watch health, browse conversations, inspect/revoke memory, and manage
  plugin and bot configuration. *(M7; bearer auth fail-closed, five
  panels, standing tool approvals, operator audit trail.)*
- [x] 7. **Operations are routine**: rate limiting and abuse guards,
  proactive messaging policy, backup/restore runbook rehearsed, pinned
  images, deployment guide, and `make verify` green in CI. *(M8; guards +
  moderation hook, opt-in proactive pass, rehearsed drill,
  `docs/DEPLOYMENT.md` + `docs/RUNBOOK.md`, pip-audit in CI, load smoke.)*

Explicit non-goals (unchanged since Milestone 1, still non-goals):
bundling NapCat into Compose, multi-tenant SaaS operation, exposing any
surface beyond loopback without an operator-provided TLS/auth proxy, and
treating containers as a sufficient sandbox for hostile plugin code.

## M2 — Messaging spine — complete

Plan: `docs/superpowers/plans/2026-07-26-messaging-spine.md`.

**Goal:** an end-to-end, at-least-once message loop on both platforms with
no LLM involvement: platform event → `MessageEnvelope` → Redis Streams →
agent-worker → rule-based `TurnDecision` → `ReplyPlan` → outbound stream →
platform delivery, with conversations and messages persisted.

**Delivered:** pure inbound translators for OneBot v11 and Telegram
`Update`s; gateway transports under the cancellable lifecycle (NapCat
WebSocket with token auth and bounded-backoff reconnect, Telegram long
polling with offset management); `mybot:ingest`/`mybot:outbound` Redis
Streams with consumer groups, explicit acks, dedupe keys, and capped
dead-letter streams; migration 0002 (`conversations`, `messages`) with
repositories; the documented turn policy (direct chats always; groups on
mention/reply/command); outbound delivery honoring
`PlatformCapabilities` and `TypingProfile`; `/ping` and `/status`
commands. CI exercises the pipeline against real Redis/PostgreSQL.

## M3 — Agent core — complete

Plan: `docs/superpowers/plans/2026-07-26-agent-core.md`.

**Goal:** replace the rule-based direct replies with a real agent turn:
LLM-generated `ReplyPlan` for both platforms.

**Delivered:** `LlmClient` for OpenAI-compatible `/chat/completions`
(bounded timeouts, retry with backoff on 429/5xx, typed errors); persona
from `system_kv` with `MYBOT_AGENT_SYSTEM_PROMPT` fallback; bounded
history window with token budgeting (chars/4 estimate); migration 0003
`turns` (decision, model, token usage, latency, outcome); model output
shaped into a validated 1–3 segment `ReplyPlan` with typing simulation;
explicit degradation (missing config, LLM outage, and budget ceilings
each produce a deterministic fallback and an accurate turn record);
per-conversation serialization; daily global and per-conversation token
ceilings backed by Redis counters.

## M4 — Tools and search — complete

Plan: `docs/superpowers/plans/2026-07-26-tools-and-search.md`.

**Goal:** the agent can decide to use tools mid-turn, execute them under
policy, and cite results.

**Delivered:** tool registry keyed by `ToolSpec` wired into the LLM
tool-calling protocol; policy enforcement (capability grants,
`approval_required` refusal until M7 added standing approvals, risk
tiers); built-in SearXNG search and URL fetch with an SSRF guard (private,
loopback, link-local, reserved, and multicast addresses denied; size and
time caps); bounded tool loop (max calls per turn, per-tool timeouts,
turn deadline degrading to fallback); every invocation audited in
`tool_invocations`; sources deduplicated into `ReplyPlan.citations` and
rendered as a `Sources:` footer.

## M5 — Memory — complete

Plan: `docs/superpowers/plans/2026-07-26-memory.md`.

**Goal:** durable, scoped, revocable memory that measurably improves
replies.

**Delivered:** embeddings via the OpenAI-compatible `/embeddings`
endpoint with credential fallback to the LLM settings; migration 0004
`memory_items` with a dimensionless pgvector column tagged by embedding
model; post-turn extraction with confidence thresholds (never SENSITIVE);
retrieval by scope + similarity under its own token budget with
provenance markers; privacy enforced in SQL and code (PRIVATE/SENSITIVE
never leaves the subject's direct chat; adversarially tested); `/forget`
with immediate revocation; the maintenance worker's first real job —
expiry, decay with a confidence floor, and revoked-item purge on a
schedule.

## M6 — Plugin system — complete

Plan: `docs/superpowers/plans/2026-07-26-plugin-system.md`.

**Goal:** third-party behavior loads from a manifest and runs in the
isolated runner with no new privileges.

**Delivered:** broker inside the API (the only component on both the
backend and internal `plugin-control` networks) with registration,
config delivery, long-poll work dispatch, and health; the runner remains
a pure HTTP client receiving only `MYBOT_PLUGIN_BROKER_URL` and
`MYBOT_PLUGIN_CONFIG`; manifests validated against `PluginManifest` with
capability grants enforced at registration (refusal + audit); plugin
tools merged into the agent registry on a TTL with built-in ids
unshadowable; read-only message event hooks; per-call timeouts, result
size caps, and crash isolation; the in-repo `example.dice` plugin as the
reference implementation; an honest statement of what the container
boundary does not defend against.

## M7 — Operator console — complete

Plan: `docs/superpowers/plans/2026-07-26-operator-console.md`.

**Goal:** the web shell becomes a real, authenticated operations console.

**Delivered:** static bearer token auth on every `/operator/*` endpoint
(fail-closed when unset, constant-time comparison, per-client failure
rate limiting; health endpoints stay open for probes); read APIs and UI
panels for overview metrics (token sparkline, turn outcomes, latency,
queue and dead-letter depths), conversation browsing down to per-turn
tool detail, memory browsing with one-click revoke, plugin status, and
persona editing picked up without restart; standing approvals for
`approval_required` tools stored in `system_kv` and refreshed by workers
on a short TTL; every mutation recorded in `operator_audit` and visible
via `GET /operator/audit`; token held in browser memory only.

## M8 — Production polish — complete

Plan: `docs/superpowers/plans/2026-07-26-production-polish.md`.

**Goal:** close the gap between "works" and "runs unattended for months".

**Delivered:** abuse and cost guards (per-user and per-chat rate limits
that refuse once then go silent, group cooldowns, input size caps,
bot-sender and echo loop detection, a `ModerationHook` ahead of
delivery); policy-gated proactive check-ins from the maintenance worker
(global kill switch, operator-managed opt-in list, UTC quiet hours with
midnight wrap, per-conversation frequency caps, recorded as `PROACTIVE`
turns); `scripts/backup.sh`/`restore.sh` with a rehearsed
backup→destroy→restore drill; Compose hardening (log rotation, memory
and CPU limits, 30-second graceful stop); `SEARXNG_IMAGE_TAG`
parameterization with documented digest pinning; a pip-audit job in CI
over production dependencies; a 100-message load smoke test through real
Redis and PostgreSQL; `docs/DEPLOYMENT.md` and `docs/RUNBOOK.md`.

## Cross-cutting rules that governed every milestone

- Test-first, in the established style: RED evidence before
  implementation, focused runs, then full `make verify`.
- No new secrets in the repository; every new setting landed in
  `.env.example` with a placeholder and in the README tables.
- Contract changes stayed additive; no breaking change proved necessary.
- Every new run surface kept the loopback-bind and least-privilege
  container defaults.
- Each milestone ended with a conventional commit and an updated README
  section for what became operable.

## Risks, revisited at the end

- **NapCat/OneBot drift** — the QQ translator is pure and
  fixture-tested; a protocol change is a fixture update, not an
  architecture change. The external-NapCat stance held.
- **LLM/provider variance** — behavior is pinned with recorded fixtures;
  the tool-calling path tolerates the common deviations. New providers
  should be run against the conformance tests before production.
- **Memory privacy regressions** — enforced in code paths and
  adversarial tests, never delegated to the prompt. Keep it that way in
  future changes.
- **Scope creep** — each plan kept a "not in this milestone" list; the
  items that accumulated there (real moderation backend, LLM-authored
  proactive content, multi-node scaling, automated offsite backup
  shipping, interactive per-call tool approvals) are the natural backlog
  beyond this roadmap.
